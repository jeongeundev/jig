# adopt — 기존 프로젝트

원칙: **코드가 사실, 문서는 주장.** 하네스는 지금 코드가 실제로 하는 것을 적는다. 기존 문서와 코드가 다르면 고치지 말고 사용자에게 묻는다.
기존 동작은 바꾸지 않는다. 이 스킬이 쓰는 파일은 하네스 파일뿐이다.

템플릿은 이 스킬 디렉토리 기준 `../../templates/` 에 있다.

## 1. 읽기
병렬로 파악한다 (규모가 크면 Explore 서브에이전트 사용):
- 기존 규칙 파일: `AGENTS.md`, `CLAUDE.md`, `.cursor/`, `.github/copilot-instructions.md`, `CONTRIBUTING.md`
- 기존 문서: `README`, `docs/`, ADR 류
- 스택: 매니페스트(`pyproject.toml`, `package.json`, `go.mod` …), 락파일, CI 설정
- 테스트: 위치·명명 규칙·러너. **실제로 실행**해서 현재 통과/실패 상태를 기록한다.
- 구조: 최상위 모듈과 의존 방향, 외부 경계(DB·HTTP·비밀값)
- 이력: `git log --oneline -50` — 커밋 규칙, 최근 작업 영역, 되돌린 커밋

## 2. 불일치 목록
읽은 것 사이의 차이를 목록으로 만든다 (문서 ↔ 코드, README 명령 ↔ 실제 명령, CI ↔ 로컬). 각 항목을 사용자에게 묻는다 — 한 번에 4개 이하, 추천을 먼저. 답으로 정해진 것만 하네스에 적는다.

## 3. 하네스 작성
기존 파일이 있으면 **덮어쓰지 않고 합친다**: 기존 내용 보존, jig 구조로 재배치, 바꾼 부분을 사용자에게 보여준다.
- `AGENTS.md`: `templates/AGENTS.md` 구조. CRITICAL 규칙은 코드에서 실제로 지켜지고 있는 경계만 (지켜지지 않는 규칙을 적으면 첫 작업부터 충돌한다).
- `CLAUDE.md`: 기존 내용이 있으면 `AGENTS.md` 로 옮기고 `@AGENTS.md` import 만 남긴다.
- `jig.json`: 1단계에서 확인한 실제 명령. `tdd` 는 **기존 테스트 배치 규칙을 그대로** 표현한다. 테스트가 없는 영역이 많으면 `source` 를 앞으로 새로 만들 영역으로 좁히고, 그 사실을 사용자에게 알린다 (기존 파일 수정마다 막히지 않게).
- `docs/`: 없는 것만 템플릿에서 만든다. `ARCHITECTURE.md` 는 1단계에서 확인한 구조로 채운다. 기존 ADR 은 그대로 두고 위치만 `AGENTS.md` 문서 표에 연결한다.
- `docs/engineering-notes.md`: 이력에서 보인 되돌림·핫픽스 중 교훈이 분명한 것만.
- 현재 실패하는 테스트가 있으면 `docs/specs/` 가 아니라 `engineering-notes.md` 「알려진 실패」에 적고 사용자에게 보고한다. 고치지 않는다.

## 4. 확인과 마무리
- `jig.json` 명령을 실행해 1단계와 같은 결과가 나오는지 확인한다.
- 커밋은 별도 브랜치에서: `chore: adopt jig harness`. main 에 직접 커밋하지 않는다.
- 보고: 만든/합친 파일, 사용자 답으로 정한 것, 테스트가 비어 있는 영역, 다음 단계 `/jig:spec`.
