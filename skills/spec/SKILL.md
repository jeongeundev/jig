# spec — 무엇을 만들지 확정

목표 하나: **설계에 들어가는 중요한 결정 중 에이전트가 사용자 대신 추측으로 정한 것이 하나도 남지 않게 한다.**
그럴듯한 기본값을 골라 넘어가는 것이 나중에 가장 비싸게 터진다. 뒤의 독립 검사를 믿고 여기를 얕게 하지 않는다 — 검사에서 무언가 나오면 이 단계의 실패다.

## 1. 맥락
`AGENTS.md` 문서 표를 따라 PRD(특히 「하지 않는 것」)·ARCHITECTURE·관련 ADR·GLOSSARY·engineering-notes 를 읽고, 바뀔 코드를 직접 읽는다. 요청이 PRD 범위 밖이면 먼저 그 사실을 말한다.
기존 코드를 바꾸는 변경이면 **현재 동작**을 먼저 적는다 (명세는 현재와의 차이로 쓴다).

## 2. 결정 목록
이번 변경이 다루는 대상(엔티티·상태·행위자·외부 연동)을 적고, 각 대상과 서로 부딪히는 쌍에 네 관점을 적용해 "설계가 답해야 하는 결정"을 뽑는다. 관점은 빠뜨리지 않기 위한 도구지 고정 목록이 아니다.
- 구조: 몇 개인가(1:1·1:N), 무엇으로 구별하나, 무엇에 속하나
- 동작: 상태 전이, 동시에 일어나면, 실패·거절·재시도, 경계 사례
- 기술: 저장, 인터페이스, 일관성, 성능
- 계약: 값 집합, 중복 기준, 응답·산출물 형식, 사용자에게 보이는 문구

결정마다 하나로 처리한다:
- **근거 있음** — 사용자가 말했거나 문서·코드가 이미 답한다 (출처를 적는다)
- **조정값** — 정한 방식 안의 숫자·한도 → 기본값을 정하고 "조정 가능"
- **묻기** — 그 밖 전부. 업무·동작은 사용자에게서 끌어내고(지어내지 않는다), 기술은 선택지·장단점·추천을 주고 고르게 한다
- **N/A — 근거** — 이번 변경과 무관한 이유

질문은 위치(어느 화면·경로·규칙), 왜 아직 답이 없는지, 놔두면 생기는 결과를 셋 다 댈 수 있는 것만. 한 번에 4개 이하, 추천을 앞에. 남으면 다음 차례에 이어서 묻는다.

## 3. 독립 검사
분류를 마치면 **항상** 결정에 참여하지 않은 서브에이전트를 1회 띄운다 (Codex 면 새 세션). 프롬프트: "파일을 수정하지 말고 목록만 반환하라". 주는 것: 사용자 발언 원문과 결정 목록. 시키는 것: ① "근거 있음"으로 처리했지만 실제 발언·문서로 추적되지 않는 것 ② 목록에 아예 없는 결정. 조정값은 지적하지 않게 한다.
결과는 문서를 고쳐 메우지 말고 사용자에게 다시 묻는다. 한 번만 반복하고, 그래도 남으면 사용자에게 넘긴다.

## 4. 작성
`docs/specs/NNNN-<slug>/` (번호는 기존 최대값 + 1):

**spec.md**
```
status: draft
# <제목>
## 왜
## 현재 동작 (기존 코드 변경일 때)
## 범위 — 하는 것 / 하지 않는 것
## 결정            ← 2단계 목록 그대로 (결정 · 처리 · 근거/답)
## 수용 기준       ← 그대로 복사해 실행할 수 있는 명령 + 기대 결과
```
**plan.md** — 작업 목록. 작업마다:
- 이름(kebab-case), 다루는 모듈 하나 (여러 모듈이면 쪼갠다)
- 먼저 쓸 테스트: 파일 경로와 검증할 동작 (`jig.json` 의 `tdd.tests` 경로 규칙을 따른다)
- 인터페이스: 시그니처 수준. 구현은 재량, 단 멱등성·보안·데이터 무결성 규칙은 명시
- 검증 명령: `AGENTS.md` 명령어에 있는 것 그대로
- 주의: "X 하지 마라. 이유: Y"
- `depends:` 앞선 작업 이름 (없으면 생략 — 병렬 가능)

새 기술 선택·되돌리기 어려운 결정이 있으면 `docs/adr/` 초안도 같이 쓴다. 새 용어는 GLOSSARY 에.

## 5. 승인
spec.md 를 요약해 보여주고 승인을 받는다. 승인되면 `status: approved` 로 바꾸고 커밋 (`docs: spec NNNN <slug>`). 다음 단계는 `/jig:build NNNN`.
