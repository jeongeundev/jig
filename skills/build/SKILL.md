# build — 승인된 명세를 구현

명세가 정답이다. 명세·계획·코드·관례가 부딪히면 명세를 따르고, 명세 자체가 틀려 보이면 **멈추고 사용자에게 묻는다** — 스스로 고치지 않는다.
완료는 캡처한 명령 결과로만 판단한다. 에이전트의 "잘 된 것 같다"는 증거가 아니다.

## 0. 준비
- 대상 명세의 `status: approved` 확인. 아니면 `/jig:spec` 으로 돌려보낸다.
- 브랜치: `feat/NNNN-<slug>` (main 에서). 작업 트리가 깨끗한지 확인.
- 시작 전 `jig.json` 의 `commands.test` 를 돌려 기준 상태를 기록한다 (이미 실패하던 테스트를 내 탓으로 착각하지 않도록).

## 1. 실행 순서
`plan.md` 의 `depends:` 로 순서를 정한다. 의존을 새로 판단하거나 바꾸지 않는다 — 이상하면 멈추고 묻는다.
- 기본: 메인 세션이 순서대로 직접 한다 (맥락이 쌓이는 게 이득).
- 서로 독립인 작업이 여럿이고 파일이 겹치지 않을 때만 서브에이전트(가능하면 worktree 격리)에 나눈다. 서브에이전트 프롬프트에는 spec.md·plan.md 경로, 맡은 작업, "사용자에게 직접 묻지 말고 막히면 BLOCKED 와 이유를 반환하라"를 넣는다.

## 2. 작업 하나의 루프
1. **Red** — plan 의 테스트를 쓴다. 실행해서 **기대한 이유로 실패**하는 것을 확인한다 (import 오류 같은 엉뚱한 실패는 Red 가 아니다).
2. **Green** — 테스트를 통과시키는 최소 구현.
3. **Refactor** — 테스트를 유지한 채 정리. 요청 밖 리팩터링은 하지 않는다.
4. **증거** — plan 의 검증 명령을 실행하고 `log.md` 에 적는다:
   ```
   ## <작업 이름>
   - red: `<명령>` → 실패 (<핵심 메시지 한 줄>)
   - green: `<명령>` → 통과 (<n passed>)
   - 계획과 달라진 점: 없음 | <무엇을 왜>
   ```
5. 커밋: `feat(<slug>): <작업 이름>` (test 와 구현을 같은 커밋에).

훅이 막으면(테스트 없음, 검증 실패) 우회하지 말고 원인을 고친다. Bash 리다이렉션으로 파일을 써서 훅을 피하지 않는다.

## 3. 리뷰 (작업 전체가 끝난 뒤)
작성에 참여하지 않은 서브에이전트에 두 관점을 맡긴다 (파일 수정 금지, 발견 목록만 반환):
- **명세 준수**: 수용 기준과 결정 목록을 하나씩 코드·테스트와 대조. 빠진 것, 명세에 없는데 추가된 것.
- **코드 품질**: `AGENTS.md` CRITICAL 위반, 테스트가 실제로 동작을 검증하는지(항상 통과하는 테스트), 보안·비밀값.
발견은 고치고 다시 검증한다. 명세 해석이 갈리는 발견은 사용자에게 묻는다.

## 4. 마무리
- 수용 기준의 명령을 전부 실행하고 결과를 `log.md` 에 적는다.
- 문서 갱신: 구조가 바뀌었으면 ARCHITECTURE, 새 결정은 ADR, 겪은 함정은 engineering-notes, 새 용어는 GLOSSARY.
- `spec.md` 를 `status: done` 으로.
- PR 생성 (`gh pr create`): 템플릿의 「검증 증거」에 log.md 요약. 병합은 사용자가 한다 — 스스로 병합하지 않는다.
- 보고: 무엇이 됐나, 증거, 명세와 달라진 점, 남은 위험.
